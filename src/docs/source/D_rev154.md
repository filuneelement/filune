D-0. 문서 사용법
이 문서는 ㉔ 산출물 D·E·F를 한 문서에 담았다. 세 파트는 각각 따로 읽을 수 있다.
파트	내용	누가 언제 쓰나
D — 품질 검사	Q1~Q14를 계산 / 명리 판단 / 고객 문장의 3단계로 나눔. 단계별 실패 사례와 수정 방법	감정서 초안을 다 쓴 뒤, 작성자가 아닌 검토자
E — 운영 단계	고객 입력부터 최종 제공까지 P1~P10. 단계마다 입력·출력·다음 단계로 넘길 정보	새 명식을 처음 받았을 때부터
F — 미확정·과제	문서 A의 미확정 규칙과, 풀기 위해 필요한 검증 과제 목록	다음 연구 단계를 정할 때
함께 쓰는 문서: 문서 A(명리 해석 기준서: C-xx, I-xx, U-xx), 문서 B(고객용 작성 기준서: W-xx, CH-xx), 문서 C(통합 검증 사례집: CS-005·126·109).
이 문서는 절차를 정의할 뿐이고, 코드·데이터베이스·프롬프트 구현은 다루지 않는다. ‘프로그램으로 재현 가능’이라는 말은 독립 만세력 도구(예: lunar_python, PyEphem)로 같은 값을 다시 얻을 수 있다는 뜻이다.

F-3. 과제를 다룰 때의 원칙
•	과제의 결과가 ‘사례 없음’이어도 기록한다. 없다는 것도 결과이다.
•	새 사례 하나로 규칙을 확정하지 않는다. 상태는 문서 A-4-2의 변경 조건을 따른다.
•	고객 반응(‘잘 맞았다’)은 규칙의 근거가 아니다. 적중 여부를 보려면 별도의 설계(미리 정한 기준, 다수 사례)가 필요하고, 그 설계는 이 목록에 없다.
•	과제 결과로 규칙이 바뀌면 순서는 문서 A → 문서 B → 문서 D → 문서 C(해당 사례 재검토)이다.

### Q16. 병(病) 판정 독립성 검사

병 회귀검증에서는 expected 병 목록과 evaluator 입력을 분리한다.

다음 값을 fixture의 확정 입력으로 직접 제공하지 않는다.

- `damage = true` 또는 `effect: "damage"`와 같이 실제 손상을 확정하는 값
- `isByeong = true`
- expected 병 역할
- expected 병 글자에서 역산한 확정 손상 상태

회귀검증 입력은 가능한 경우 다음의 독립 사실로 구성한다.

- 원국 및 운의 entity
- 십성 및 구조상 역할
- 방향성 있는 관계
- 합·충 등의 관계
- runtime state
- 통근·투출 등 필요한 구조 Fact
- 독립 producer가 생성한 evidence 및 provenance

**독립 회귀검증**에서는 evaluator가 이 입력과 현행 Rule을 사용하여 손상 여부와 병 역할을 독립 산출한다. expected 병 목록은 산출 이후 비교에만 사용한다. 독립 근거가 부족하면 판단 보류가 기대되는지를 검증한다.

**계약 테스트(contract test)**에서는 합성된 `damage` 관측을 입력해 evaluator의 입력 검증, 상태 처리 또는 출력 계약을 확인할 수 있다. 이 결과는 독립 회귀검증 통과로 집계하지 않는다.

병 회귀검증에는 최소 다음 반례를 포함한다.

1. 같은 오행이지만 손상 상대가 달라 병이 아닌 경우
2. 생 관계는 있으나 실제 보호 기능 손상이 없는 경우
3. 제어가 성공하여 병이 성립하지 않는 경우
4. 병이 `stopped`된 경우
5. 병이 `weakened`된 경우
6. 일부 관계만 확인되고 핵심 손상 근거가 없어 `deferred`가 되는 경우
7. 복수 병 중 하나만 제거되는 경우
8. 조사 범위가 완전하여 실제 `no-byeong`으로 판정되는 경우

회귀검증은 `has-byeong / no-byeong / deferred`를 각각 독립적으로 검증한다.
