FILUNE CS-005 최소 계약 세트 — 확정 설계안

이 문서는 여섯 기술 계약의 필드·경계·불변조건을 정의한다. 명리 판정 규칙,
지장간 데이터, 사례 입력/기대값 fixture, 실행 가능한 타입/코드를 생성하지 않는다.
“확정 설계”는 이 보고서가 선택한 기술 구조를 뜻하며 운영자의 명리 승인으로
기록하지 않는다. 원문에 없는 역할 선정·강도·발행 기준은 추가하지 않는다.
기준: 기존 preflight, A rev179, C rev215, D rev152, 25-7 rev16.

0. 공통 표기와 최소 범위

필드 표의 required는 runtime 계약을 충족하려면 있어야 한다는 뜻이다.
unknown은 null/빈 배열/false/active로 대체하지 않는다.
아래 ID는 모두 비어 있지 않은 문자열 참조다. 참조 대상의 존재와 같은 평가
context/문서 revision 소속을 검증해야 한다. ID 문자열 형식 자체는 명리 규칙이 아니다.

공통 값 표기(별도 일곱 번째 계약을 추가하지 않고 여섯 계약 안에서 재사용):
- FactStatus: confirmed / provisional / unknown / unsupported (기존 ValueStatus 의미 유지).
- 기간: 기존 운/절입 카드의 periodRef를 우선 참조. 경계가 정확하면 UTC ISO instant,
  불확실하면 범위 또는 unknown을 명시한다. 유효 구간은 기술적으로 [from,to)로
  표현하고 경계값을 새로 계산하지 않는다. 원문이 대략 시점만 제공하면 exact로 승격 금지.
- EntityRef: entityId, origin(natal/great/year/month), part(stem/branch),
  canonicalFactRef, periodRef(운일 때), position(원국일 때만).
  동일 글자도 원국/대운/세운/월운 및 자리별로 서로 다른 entityId다.
- ScopeRef: scopeId, stage(natal/great/year/month), targetPeriodRef,
  directEntityIds, inheritedChangeIds, priorProcessingRefs, evidenceIds.
  scope의 유효성을 OP-L01/OP-L02에 따라 판단하는 것은 향후 Rule 실행이다.
  계약은 선언과 판정 결과를 구별해 scopeApprovalApplicationRef를 보관한다.
- ApplicationRef: execution context + scope + Rule ID + ruleVersion + applicationId.
  하나의 Rule ID를 여러 운/기간에 실행할 수 있으므로 ID를 Rule ID만으로 만들지 않는다.
- uncertaintyIds: 항상 존재하는 배열. 빈 배열은 검토 누락을 숨기는 의미가 아니다.

여섯 계약의 연결:
EvidenceContext → HiddenStemSystem / RelationFact의 출처
RelationFact(존재) → 향후 Rule 실행 → RuntimeState(작용)
RuntimeState의 원국 변화 → LuckCarryState
RoleState의 근거 있는 역할 + RuntimeState → 향후 상신 기능 등 판단
OperatorReview/Publication은 이 연결 밖이며 문서 상태와 자동 대응하지 않는다.

최소 단계는 entity별 관계·기능·원국 변화·승계의 추적이다. “상신 丙 유지”라는
역할 포함 결론은 역할 선정 application 또는 명시적으로 허용된 역할 입력이 있어야
한다. 이번 보고서는 CS 기대 역할을 runtime 입력으로 주입하도록 허용하지 않는다.

1. HiddenStemSystemContract

기준 원문: A C-10, A-8-1 I-02·C-10, IR-02; D H-3-1.
현재 문서상 FILUNE 기본: 본기·중기·여기 체계.
다른 체계: 월률분야 일수 체계는 별도 층위. 두 목록을 한 표/판정 입력에 섞지 않는다.

필드 | 타입/제약 | 필수
systemId | 버전이 고정된 체계 식별 ID; runtime에서 임의 기본값 선택 금지 | required
systemName | 원문 체계명 문자열 | required
systemVersion | 데이터 버전 식별 문자열 | required
usage | default-judgment / separate-reference | required
semanticRoles | main=본기, middle=중기, residual=여기 | required
semanticOrder | [main,middle,residual] 기술상 표준 열거 순서 | required
sourceDisplayOrder | 원문 표에 실제 사용된 순서; D H-3-1은 [residual,middle,main] | required
entriesRef | 명시적 체계 데이터 집합 참조; 이 보고서에서는 데이터 미생성 | required
entryShape | branch + roles{main:stem,middle?:stem,residual?:stem} + evidenceIds | required
sourceRefs | EvidenceContext의 원문 참조 ID 배열 | required
compatibility | {legacyTableRef,status:verified/mismatch/not-checked,comparisonEvidenceIds} | required
assessment | FactStatus; 문서 체계 호환성 검증 결과와 구분 | required
uncertaintyIds | ID 배열 | required

기술 결정:
- 의미 식별은 배열 인덱스가 아닌 role key다. semanticOrder는 새 지장간 구성이 아니다.
- 원문/기존 UI의 “여기→중기→본기” 표시 순서는 sourceDisplayOrder에 보존한다.
- 해당 지지에 없는 middle/residual은 생략 가능하나, 목록이 미확인인 경우와
  확인 결과 그 역할이 없는 경우를 entries 데이터의 completeness로 구별한다.
- main이 없는 데이터는 미완전/미확인이고 임의 추정하지 않는다.
- 다른 체계는 systemId별 독립 entriesRef로 병존한다. 소비자는 한 판단에서
  어떤 systemId를 썼는지 명시하며 다른 체계 글자를 자동 합치지 않는다.
- 역할표 데이터 자체는 변경하지 않는다. 원문에서 명시된 글자·역할만 공급해야 한다.

기존 코드와 실제 차이:
HIDDEN_STEM_ROLE_TABLE은 子에 壬/癸, 亥에 戊/甲/壬을 가진다.
D H-3-1 NT-03은 子에 癸만 기재하고 C C-10-1 CS-109는 기본 체계 亥에 戊가
없다고 명시한다. 따라서 기존 표를 이름만 바꾸어 default-judgment에 배정할 수 없다.
CS-005 사용 지지에 대해서도 row별 원문 대조가 필요하다. 새 표를 이 보고서에서
제작하거나 특정 글자만 임의 제거하지 않는다. 불일치 데이터는 별도 legacyTableRef로 보존한다.

CS-005 필수:
systemId/name/version, default usage, role key/order, 사용 지지의 entriesRef,
각 row evidenceIds, legacy compatibility 결과, uncertaintyIds.
전체 12지지 완성은 최소 구조 관측에 항상 필요한 것은 아니지만 미공급 지지가
새 운/테스트에 나타나면 해당 입력을 확정으로 처리할 수 없다.

2. RelationFactContract

기준: A C-11, I-06·I-07, OP-L01, OP-Z03·04·10.
이 계약은 관계 존재만 담는다. 유효 상대 선택·합거·강약·역할·길흉은 포함하지 않는다.

필드 | 타입/제약 | 필수
relationFactId | 관계 조사 결과 ID | required
kind | stem-combination / stem-generates / stem-controls / branch-six-combination / branch-half-combination / branch-three-combination / branch-season-combination / branch-clash / branch-punishment / branch-harm / branch-break / branch-wonjin | required
participantEntityIds | 중복 없는 entity ID 배열; 동일 글자 다른 entity 허용 | required
sourceEntityId,targetEntityId | 생/극의 방향; 무방향 관계에는 없음 | 조건부 required
scopeRef | ScopeRef; 관계가 관측된 비교 범위 | required
existence | present / absent / unknown | required
coverageRef | 조사 대상 entity·관계 종류·조사 완료 상태의 참조 | required
producerRef | 기존 함수/테이블/문서의 실제 공급자·버전·입력 참조 | required
inputFactIds | 값의 원래 fact ID 목록 | required
assessment | FactStatus | required
evidenceIds,uncertaintyIds | 참조 배열 | required
natalPositionRefs | 원국 참가자 위치 참조; 운에는 위치/거리 의미를 부여하지 않음 | 원국 관계에 필요

coverage의 최소 구조:
{coverageId,scopeRef,kind,universeEntityIds,investigatedParticipantSets,
 completion:complete/partial/unknown,producerRef,evidenceIds,uncertaintyIds}

불변조건:
- absence는 해당 참가자/종류의 조사가 완료된 경우에만 허용한다.
  공급 함수가 없거나 조사하지 않았으면 unknown/partial이지 absent가 아니다.
- 삼합/방합은 다자 관계를 표현한다. 두 글자만 있다고 완성 상태로 적지 않는다.
  반합은 별도 kind다. 형도 원문/공급자의 참가자 구성대로 보존한다.
- 천간 극과 “천간충”을 동일 작용 두 건으로 중복 생성하지 않는다(I-07).
  기술 enum에 독립 stem-clash를 추가하지 않는다.
- 동일 scope/kind/방향/참가자 집합의 중복 fact를 만들지 않는다.
  이 중복 제거는 반복 육합의 서로 다른 entity 참여를 제거하지 않는다.
- OP-L01 월운 직접 관계에 대운 entity를 넣지 않는다. 대운 출처를 설명하는
  evidence/sourceRef는 존재 가능하나 참가자나 directEntityIds가 될 수 없다.
- 각 관계에는 이 계약에서 functionalState, favorable/unfavorable, 상신/병을 넣지 않는다.

공급 결정:
현재 src/lib에서 확인된 DayRelationships는 십성·지장간이며 합·충 전체 함수가 아니다.
새 관계 공식을 만들지 않고 재사용할 공급자/승인된 사실 데이터의 버전을 확인해야 한다.
계약 설계만으로 producerRef를 가짜 함수명으로 채우지 않는다.

3. RuntimeStateContract

기준: A OP-T01·02·04·07·08·10, OP-Z01·02·05, OP-L02.
요청된 여섯 단어는 기술 상태로 모두 표현하되 서로 다른 축을 한 enum으로 섞지 않는다.

필드 | 타입/제약 | 필수
stateId | immutable 상태 기록 ID | required
targetEntityId | 상태가 적용되는 entity | required
scopeRef | 적용 scope/기간 | required
functionalState | active / weakened / stopped / unknown | required
originMode | local / inherited | required
transition | established / unchanged / restored / unresolved | required
priorStateRef | 이전 기록 참조 | 전이가 있을 때 required
causingApplicationRefs | 결과를 만든 Rule 실행 참조 | 결정된 state에 required
evidenceIds,uncertaintyIds | 근거/불확실성 | required
validityRef | 유효 운 기간/경계 참조 | required
weakeningDescription | 원문 표현·해당 Rule ID; 정성 범주 | weakened일 때 required
supersedesStateRef | 앞 기록을 이력이 남는 방식으로 대체할 때 참조 | optional

여섯 상태의 기술적 의미:
active: 해당 범위에서 기록된 기능 정지/약화 결과 없이 기능 유지로 판정된 상태.
        아직 평가 전이라는 이유만으로 active를 초기값으로 넣지 않는다.
weakened: 해당 규칙의 약화 결과가 기록된 상태. percentage·점수 없음.
stopped: 해당 규칙의 합거 등에 따른 기능 정지 결과. 지지 육합을 이 값으로 만들지 않음.
inherited: 기능 상태가 아닌 originMode. stopped+inherited를 동시에 표현 가능.
restored: 이전 유효 제약의 종료/해제에 대한 근거 있는 전이 기록. 독립 새 명리 법칙 아님.
unknown: 평가/입력/근거 부족으로 기능 상태 미확정. 중립·불리·약화로 바꾸지 않음.

restored 제약:
- 같은 천간이 다시 등장했다는 이유로 restored 금지(OP-T08).
- 상위 운이 끝났다는 사실로 그 운 효과의 종료는 기록할 수 있지만,
  다른 유효 제약이 남는다면 무조건 active로 복원하지 않는다.
- 해당 기간의 제약 집합과 원국 기본 상태를 다시 참조한 application 결과가 있어야 한다.
- 첫 CS-005 관측이 종료 경계를 지나지 않으면 restored는 미사용이 정상이다.

functionalState는 문서 길흉 enum과 다르다. 오행 강화·지지 원래 성질 유지,
충 존재/영향 약화는 관계별 application 결과에 남긴다. 지지 자체 기능과 충의 영향력을
같은 targetEntityId 상태에 덮어쓰지 않는다. 예컨대 충의 약화는 해당 relation 결과를
가리키며 지지 전체가 일괄 weakened라는 새 결론을 만들지 않는다.
그 관계 결과는 RuntimeState의 evidence/application 참조로 연결한다.

4. LuckCarryStateContract

기준: A A-8-6 OP-L01·OP-L02, A-8-9 IR-01.
carry 대상은 상위 운이 남긴 원국 변화다. 상위 운 글자 또는 운끼리 약화 자체가 아니다.

필드 | 타입/제약 | 필수
carryEntryId | 승계 기록 ID | required
changeId | 최초 원국 변화 ID; 승계해도 동일 ID | required
natalEntityId | 변경 대상 원국 entity만 허용 | required
sourceStage | great / year (해당 변화 생성 단계) | required
sourceScopeRef,sourceSnapshotRef | 최초 생성 scope/snapshot | required
sourceStateRef | 최초 변화의 RuntimeState 참조 | required
causedByRuleIds | 최초 application에 실제 존재하는 Rule ID 목록 | required
causedByApplicationRefs | 실제 실행 instance 참조 | required
validFrom,validTo | 기존 period/boundary 참조; 정확/범위/미확인 구별 | required
inheritedIntoScopeRef | 이번 승계 대상 scope | required
inheritedThrough | 경유 scope 참조 배열; 재생성된 변화로 세지 않음 | required
evidenceIds,uncertaintyIds | 근거/불확실성 | required

stage snapshot 안에서 분리할 여섯 칸:
1 natalStructureRefs
2 natalInternalStateRefs
3 inheritedNatalChangeRefs
4 currentLuckPairApplicationRefs
5 currentLuckNatalApplicationRefs
6 outgoingCarryEntryRefs
명칭은 OP-L02 여섯 정보의 기술 저장 위치다. 완전한 판단 결과를 미리 넣지 않는다.

중복 재계산 금지용 처리 이력(동 계약의 별도 ledger 부분):
processedRelationRecords:
 {processingId,sourceScopeRef,relationFactRef,applicationRef,
  targetNatalEntityIds?,affectedLuckEntityIds?,effectClass,
  sourcePeriodRef,evidenceIds}
consumedAtStage:
 {scopeRef,changeId,consumptionRef,sourceApplicationRef}

중요 구분:
- 운끼리 약화 결과는 carryEntry에 들어갈 수 없다.
- IR-01이 요구하는 “상위 단계에서 이미 처리한 세운–원국 관계를 월운에서
  새 합거로 계산하지 않음”을 확인하기 위해 과거 처리 ledger를 조회한다.
- 세운이 대운과 합해 약해졌다는 과거 기록을 읽어 IR-01의 재합거 금지 여부를
  확인할 수 있지만 그 약화 상태를 월운 active set으로 복제하지 않는다.
- ledger의 운 entity는 과거 기록 참조이며 월운 directEntityIds/관계 참가자가 아니다.
- 새 eligibility/우선순위를 ledger가 결정하지 않는다. OP-L01/L02/IR-01을
  사용하는 향후 application이 ledger를 근거로 중복 여부를 기록한다.

불변조건:
- 같은 changeId를 같은 scope에서 두 번 소비하지 않는다.
- carry는 기존 기능 상태를 참조하며 새로운 합거 application을 만들지 않는다.
- 원국 내부 합거는 natalInternalStateRefs에 있고 “대운이 만든 변화”로 위장하지 않는다.
- source validity 밖으로 승계하지 않는다. validTo 미확인이면 종료를 추정하지 않는다.
- 사실상의 소급 적용 금지: 월운 부모 세운은 기존 절입 기간으로 선택한다.
  CS-005의 2027.1 辛丑은 입춘 전 丙午 세운 소속이다.
  丁未 세운 snapshot은 별도이며 그 결과를 2027.1에 승계하지 않는다.
- 기존 카드가 단일 정밀 시각만 가지는데 원문은 교운 범위이면 원문 범위를 증거로
  병존시키며 단일값을 문서 확정값으로 승격하지 않는다.

5. EvidenceContextContract

sourceType enum:
customer-input / source-document / deterministic-calculation /
independent-cross-check / reverse-inference / operator-confirmed.
이는 출처 분류이며 신뢰 순위나 자동 승인 순서가 아니다.

필드 | 타입/제약 | 필수
evidenceId | 증거 ID | required
sourceType | 위 여섯 값 | required
sourceRef | tagged source reference(아래) | required
documentRevision | 원문 문서가 있는 유형은 정수; 그 외 null | required key
ruleId | 직접 관련 Rule ID; 문서 직접 연결이 없으면 null | required key
hash | {algorithm:SHA-256,value,hashTarget}; 실제 산출한 해시만 | optional
status | confirmed / provisional / unknown / unsupported | required
verification | {claimRef,method,checkedByRef?,basisEvidenceIds,checkedAt?} | required
note | 원문 제한·역산·불일치 설명; 없으면 빈 문자열 | required
uncertaintyIds | ID 배열 | required
usage | runtime-evidence / rule-definition / regression-expectation / audit-only | required
sourceLayer | 원문이 명시한 S1~S5/OP 등; 추정하여 부여하지 않음 | optional

sourceRef variant:
customer-input: 원래 입력 기록 ID·필드 경로·수신 기록 참조.
source-document: 문서 ID·파일 경로·revision·section·행/문단 위치.
deterministic-calculation: 기존 함수/도구·버전·입력 fact refs·출력 refs·시간정책 참조.
independent-cross-check: 서로 다른 관측 refs 둘 이상·독립성 설명·대조 결과·검토 기록.
reverse-inference: 후보 목록 refs·채택 근거·역산 대상 필드·원문 refs.
operator-confirmed: 결정 기록 ref·승인 범위·관련 원문 refs.

검증 상태의 기준:
- status는 verification.claimRef의 명제에 대한 상태다.
  “문서가 존재함”과 “출생 날짜가 사실임”은 서로 다른 claim/evidence다.
- confirmed는 해당 명제를 그 검증 방법·근거 범위에서 확인했다는 기록이다.
  파일을 읽을 수 있음, YAML revision 일치만으로 계산·사건 사실을 confirmed하지 않는다.
- operator-confirmed도 원전 S2·전문가 S3·예측 적중 확인으로 바뀌지 않는다.
- reverse-inference는 원문과 후보 채택 절차를 확인할 수 있어도 역산 날짜의
  실재 확정을 의미하지 않는다. 절차 확인 claim과 날짜 claim을 분리한다.
- confidence 수치 필드는 만들지 않는다. sourceLayer/FactStatus/verification을 분리한다.
- independent-cross-check는 같은 도구 재실행/그 결과 projection으로 대체 불가.
  두 producer의 계산 계통·입력/시간대·버전·대조 내용을 확인해야 한다.
- 증거가 부족하면 provisional/unknown과 uncertaintyIds를 기록한다.
- regression-expectation은 evaluator 입력으로 전달하지 않는다. 같은 원문 안에서도
  출생 간지 사실 claim과 기대 판정 claim을 별도 ID/usage로 분리한다.
- ruleId:null은 “문서상 직접 참조 없음”이며 임의 추론 ID로 채우지 않는다.
- hash는 내용 식별 도구이며 명제의 참/거짓 또는 운영 승인을 입증하지 않는다.

CS-005 필수 evidence claim:
원국 출처 / 역산 날짜·후보·채택 근거 / 戌시 범위 / 지장간 체계와 legacy 대조 /
기존 계산 버전·시간정책 / 독립 대조 유무 / 문서 규칙 revision /
관계 공급자 출처 / 상태·carry application 근거.
해시 없는 출처는 optional hash를 생략할 수 있으나 sourceRef까지 생략하면 안 된다.

6. RoleStateContract

기준: A I-03, A-8-1·A-8-2. 여기서는 역할 선정·성패 공식을 만들지 않는다.

필드 | 타입/제약 | 필수
roleStateId | 역할 기록 ID | required
subjectKind | entity / structure | required
entityId | 용신/상신/병/구응 등 글자 대상이면 entity ID; 구조 대상이면 null | required key
structureRef | 격 등 구조 대상이면 구조 참조; entity 대상이면 null | required key
role | 격 / 용신 / 상신 / 병 / 구응 | required
status | asserted / evaluated / deferred / unknown | required
sourceRuleIds | 직접 적용·인용된 Rule ID 배열; 미확인 연결 임의 생성 금지 | required
evidenceIds | 근거 참조 배열 | required
validScope | scope·기간 참조 | required
provisional | boolean; 근거 불확실성의 표시 | required
uncertaintyIds | ID 배열 | required
origin | document-assertion / rule-result | required
applicationRef | rule-result의 실제 실행 참조; document-assertion이면 null | required key
usage | reference-only / runtime-result | required

구별 원칙:
- 격은 개별 글자에 항상 귀속되지 않는다. structureRef가 있어야 하며 entityId를
  억지로 일간 등으로 채우지 않는다.
- asserted는 문서에 역할 판단이 적혀 있다는 뜻. 자동 평가 완료라는 뜻이 아니다.
- evaluated는 해당 역할을 실제로 생성한 application과 evidence가 있을 때만 허용.
- 문서 C의 “상신 丙”은 regression/reference claim으로 보존할 수 있지만
  이를 자동 runtime assignment로 가져와 같은 답을 검증하지 않는다.
- 이번 단계는 RoleState의 schema만 설계한다. 어떤 entity에도 역할값을 채우지 않는다.
- runtime-result가 필요하나 자동 선정 application이 없으면 deferred/unknown이다.
  문서 assertion을 runtime 입력으로 허용하는 별도 수동 경로는 이번에 승인하지 않는다.
- provisional:false는 예측 확실성이나 operator auto-approved를 뜻하지 않는다.
- 역할과 기능 상태는 독립이다. 합거 때문에 투출/격 이력을 지우거나 상신이라는
  역할명을 삭제하지 않는다. 현재 기능은 RuntimeState 참조로 따로 평가한다.
- 같은 entity의 복수 역할 가능성을 schema에서 임의 금지하지 않는다.
  역할 간 실제 정합성은 원문 근거/향후 판단의 책임이며 새 공식을 만들지 않는다.

7-4. 아직 사람 결정이 필요한 필드/공급
(1) HiddenStem.entriesRef와 legacy compatibility의 근거 있는 데이터 공급 방식.
    원문 체계 선택 자체는 A에서 확정되어 있으며 새로운 학설 승인을 요청하는 것이 아니다.
(2) Relation.producerRef의 실제 기존 함수/자료 및 조사 coverage의 책임 주체.
(3) Evidence의 독립 대조 observation·checkedByRef, 시각 범위/역산 provenance 공급.
(4) Role.runtime-result를 생성할 판단 범위 또는 수동 assertion 사용 여부.
    이 보고서는 수동 기대 역할 주입을 허용하지 않는다.
(5) validFrom/To가 범위인 원국 변화에 대한 공급 증거와 해당 시점 membership의
    미확정 처리. 정확 경계를 임의 고르지 않고 unknown/deferred를 유지하는 것이 기본이다.
기술 enum/필드 이름은 이 보고서에서 설계했지만 데이터/판단 provenance가 공급됐다는
뜻은 아니다. 계약을 만들기 위해 새 외부 전문가 자료를 선행 조건으로 요구하지 않는다.

7-5. 기존 judgment/types.ts 충돌/공백
- JudgmentFact.canonicalPointer:string은 derived/document origin을 표현하지 못한다.
  canonical/derived/document origin discriminant 또는 별도 typed 계약 연결이 필요하다.
- JudgmentEvidence.rule:RuleReference는 모든 입력 증거가 규칙 실행 결과인 것으로
  모델링한다. 고객 입력·역산·도구 관측은 별도 EvidenceContext에서 연결해야 한다.
- RuleApplication.result:JsonValue만으로 상태·역할·carry 불변조건을 보장할 수 없다.
  위 계약의 출력 schema 및 참조 검증과 연결해야 한다.
- Application ID가 현재 evaluator에서 application:{rule.id}이고 dependency 조회도
  Rule ID 기준이다. 같은 규칙을 원국/대운/세운/월운에 반복할 때 scope별 실행
  instance 식별과 과거 처리 ledger가 필요하다. 원문 참조 cycle을 실행 dependency로
  옮기지 않는다.
- 현 evaluateJudgments는 fromCanonical(chart)만 fact로 받고 별도 계약 공급 경계가 없다.
  타입 파일 선언만으로 evidence/관계/state가 공급되지 않는다.
- OperatorReview는 별도 보존하며 문서 literalStatus와 변환하지 않는다.
  completeness complete가 계약 충족·발행 가능을 뜻하지 않는 점도 유지한다.
이번 작업에서는 위 타입/evaluator/registry를 수정하지 않았다.

7-6. CS-005 minimal slice 구현 시작 가능 여부: NO

여섯 계약의 schema 설계는 정의되었지만 실제 공급자/기준 데이터/증거가 아직 없다.
NO→YES는 타입 이름을 정하는 것만으로 성립하지 않는다. 현재 명시된 제약 아래
미확인 관계 계산기를 새로 만들거나 문서의 역할 정답을 미리 넣어 YES로 바꾸지 않는다.
계약 타입 선언 작업과 실제 CS-005 명리 evaluator 착수는 별도다.

7-7. 남은 blocker (최대 5개)
1. 사용 지지의 문서 기본 지장간 데이터와 legacy 표 차이의 검증·공급 미완료.
2. 합/생극/지지 전체 관계의 재사용 가능한 producer 및 coverage 공급 미확정.
3. 출생 범위·역산·독립 계산 증거의 런타임 공급 미완료.
4. 역할/실제 기능 판단을 정답 주입 없이 생성할 실행 범위·근거 공급 미확정.
5. scope별 application ID·기간·IR-01 처리 ledger를 수용할 기존 실행 경계 연결 미설계 상태.
   위에서 필요한 연결 요구사항은 정의했지만 기존 코드에 통합한 것은 아니다.

마지막 blocker는 “타입 구현이 아직 안 됐다”만을 이유로 착수를 막는다는 뜻이 아니다.
현재 한 Rule ID당 한 실행인 API를 여러 운 snapshot과 어떻게 연결할지, immutable
상태 공급을 호출자/실행기 중 누가 담당할지의 책임 계약을 먼저 결정해야 한다는 뜻이다.

구현 시작을 YES로 바꾸는 최소 충족 조건:
- 필요한 체계 row/관계 후보/출처가 버전 고정된 공급자로 추적 가능.
- 원문 범위와 절기 기간을 지키는 snapshot 및 application identity가 일관됨.
- 역할 결과가 필요한 단계와 단순 기능 상태 단계의 경계가 명시됨.
- 기대값은 검증 경로에만 있고 runtime 입력을 오염시키지 않음.
- 미확인 입력은 unknown/deferred이며 임의 계산·정답/승인 주입이 없음.

설계 보고서만 작성했다. evaluator·타입 코드·fixture·test·UI·기존 mapping은 변경하지 않았다.
